# CS-255 System Analysis and Design

This repository contains my work for CS-255: System Analysis and Design at Southern New Hampshire University.

## Projects Included
- Business Requirements Document (Project One)
- System Design Document (Project Two)

## Reflection

**Brief summary of the DriverPass project**  
The client was DriverPass, a company that wanted a system to help students prepare for their DMV driving tests. They needed a web-based system that supported online classes, practice tests, scheduling of on-the-road driving lessons, role-based access for different users (customers, secretary, drivers, IT admin, and owner), activity tracking, and integration with the DMV for content updates.

**What I did particularly well**  
I did well at capturing the client’s functional and nonfunctional requirements from the interview transcript and creating clear UML diagrams. My model application short paper and comparison of process versus object modeling also received strong feedback.

**What I would revise**  
If I could revise one part of my work, I would improve the high-level objectives and goals in the Business Requirements Document so they are more clearly separated from detailed functional requirements. I would also make the technical requirements more specific and testable (for example, listing exact hardware, software, and infrastructure details) and correct the END symbol notation in the activity diagrams. Additionally, I would strengthen the client presentation by starting with a clear system description of what functions the system will perform and grouping interface requirements by user type.

**How I interpreted the user’s needs**  
I carefully reviewed the DriverPass interview transcript multiple times, identified the different user roles, and translated their needs into system functions, diagrams, and requirements. Considering the user’s needs is critical because a system only succeeds if it solves real problems for real people and supports every role effectively.

**How I approach designing software**  
I approach software design by first gathering and clarifying requirements, then creating process and object models, followed by UML diagrams. In the future I will focus more on making goals high-level and measurable, writing testable technical requirements, and ensuring every diagram uses correct UML notation.
